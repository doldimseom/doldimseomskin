## B. 이미 있는 것 — 새로 만들 필요 없는 항목

제안서에 신규 기능으로 적힌 것 중 v1.2.0에 실물이 있는 것들입니다. 재사용하면 개발량이 눈에 띄게 줄어듭니다.

| 제안서 항목 | 현행 구현 |
| --- | --- |
| 그리드 / 리스트 뷰 전환 | `setLayout()` + `localStorage` 기억 |
| 카테고리별 홈 섹션 구성 | `buildSections()` — 카테고리 모달 순서대로 정렬, 미분류 후치 |
| 보호글 컨셉 UI | `.protected-form-wrap`, `.card-protected-overlay` — **문구·연출만 갈아끼우면 됨** |
| 티스토리 기본 UI 은닉 | CSS + `MutationObserver`로 공감(`.txt_like`, `[id^="reaction-"]`) 제거 |
| 에디터 무코딩 입력 | 제목 태그 파싱 관례 `[OPEN]` `[CLOSE]` `[PRICE:]` `[SUB:]` |
| 다른 글 본문을 현재 페이지에 렌더링 | `loadInfoSection()` — `fetch` → `DOMParser` → 불필요 요소 제거 → 삽입. **로그 렌더러(§3.2)가 그대로 따라갈 선례** |
| 카드 썸네일 / 기본 썸네일 폴백 | `thumbFallback` 옵션 |
| 테마·폰트 스케일·열 수·라운딩 옵션 | `index.xml` variablegroup |

## C. 리스크 — 설계 확정 전에 깨질 수 있는 지점

### C-1. 첨부파일 렌더링의 CORS (심각도: 높음)

제안서 §3.2는 이 스킨의 최대 셀링 포인트인데, **성립 여부가 검증되지 않은 전제 위에 있습니다.**

* 첨부파일은 블로그 도메인이 아니라 카카오 CDN에서 서빙됩니다. 브라우저 `fetch`는 CDN이 `Access-Control-Allow-Origin`을 내주지 않으면 차단됩니다.
* 기존 `loadInfoSection()`이 잘 도는 건 **같은 도메인(same-origin)** 이라 그렇습니다. 첨부는 사정이 다릅니다.
* 티스토리가 `.html` 첨부 자체를 막을 가능성도 있습니다.

→ **테스트 블로그에 코코포리아 로그를 한 번 첨부해 발행하고, 콘솔에서 `fetch(첨부URL)`을 때려보는 것**이 다른 무엇보다 먼저입니다. 여기서 막히면 §3.2의 UX 자체를 다시 짜야 합니다 (조율본 §4.1에 대안 3안 적어뒀습니다).

### C-2. 보안 — 외부 파일을 `innerHTML`로 넣지 않기 (심각도: 중)

로그 파일은 유저 자신의 파일이지만, 코코포리아/롤20 로그에는 **세션 참가자들이 입력한 텍스트**가 그대로 들어 있습니다. 파싱한 내용을 `innerHTML`로 주입하면 스크립트가 실행될 수 있습니다. 텍스트 노드 조립이나 허용 태그 화이트리스트를 거쳐야 합니다.

### C-3. 대용량 로그 성능 (심각도: 중)

세션 하나가 수천 줄입니다. 전부 DOM에 꽂으면 모바일에서 스크롤이 죽습니다. 분할 렌더링이 필요합니다.
참고로 제안서가 지적한 "에디터 렉"의 원인도 결국 같은 문제(거대 DOM)라, **첨부 방식으로 옮긴다고 자동으로 해결되지는 않습니다.**

### C-4. 카테고리명 기반 라우팅의 취약성 (심각도: 낮음~중)

유저가 스킨 옵션에 적은 카테고리명과 실제 카테고리명이 어긋나면(오타, 이름 변경, 하위 카테고리, 한글 URL 인코딩) 템플릿이 통째로 안 뜹니다. 조율본 §2.2에 예외 처리와 폴백 조건을 명시해 뒀습니다.

### C-5. Hover 레퍼런스와 미니멀리즘의 충돌 (심각도: 낮음)

VHS / kinetic text 계열은 화려한 쪽이라, 제안서가 동시에 요구하는 "테두리·그림자 배제 미니멀리즘"과 방향이 반대입니다. **효과를 2~3종으로 고정해 일관 적용**하는 편이 낫습니다. 그리고 모바일에는 Hover가 없으므로, Hover에만 담긴 정보(이면 설정 등)는 tap 폴백이 반드시 필요합니다.

### C-6. 범위 (심각도: 중)

원본 제안서는 기능 밀도가 스킨 하나치고 큽니다. 검증 안 된 §3.2와 확실히 되는 §3.4가 한 배를 타면 릴리스가 통째로 늦어집니다. 조율본 §5에 v2.0 / v2.1 / v2.2로 쪼개 뒀습니다.

## D. 결정 사항

1. **신규 스킨 vs 기존 스킨 확장** → **별도 스킨으로 신규 제작** (확정)
   현 리포지토리의 커미션/허브용 「돌딤섬 공방 스킨」과 분리합니다. 공통 로직은 v1.2.0에서 이식하되, 이후 두 스킨은 독립적으로 갑니다. 조율본 §1.1에 반영했습니다.
2. **§3.1 홈 구성 (커버 A안 / 옵션 프리셋 B안)** → **커버 자유도 검증 후 결정** (보류)
   v2.2 단계 항목이라 지금 확정하지 않아도 일정에 영향이 적습니다. 조율본에는 2안을 병기해 뒀습니다.

### 남은 확인 요청

**§4.1 검증은 티스토리 계정에서만 가능해 제가 대신 돌릴 수 없습니다.** 아래만 확인해 주시면 §3.2 설계를 바로 확정합니다.

1. 테스트 블로그에 코코포리아 로그 파일(`.html`)을 첨부해 발행 → **첨부 자체가 되는지**
2. 발행된 글에서 브라우저 콘솔에 `fetch('첨부파일URL').then(r => console.log(r.status))` → **CORS 통과 여부**
3. 실패 시 콘솔 에러 메시지 원문

## E. 권장 진행 순서

1. ~~신규 스킨 / 기존 확장 결정~~ → 완료 (별도 스킨)
2. **§4.1 CORS·첨부 검증** (계정 필요) → §3.2 확정
3. 로그 백업 첨부파일 렌더링 스크립트 구상 + 전체 CSS 레이아웃(그리드/템플릿) 마크업 구조 제시 — 원본 §4의 착수 산출물
4. v2.0 구현 (§2 라우팅, §3.2 로그 렌더러, §3.3 캐릭터 갤러리, §3.5 표기 규칙)

2번이 막혀 있어도 3번의 **CSS 레이아웃·마크업 구조**는 선행 가능합니다. 로그 렌더러도 파일을 가져오는 부분만 분리해 두면 첨부 방식이 무산되어도 나머지 파서·뷰어는 그대로 씁니다.
